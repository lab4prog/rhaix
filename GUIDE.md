# rhaix — короткий посібник

Як створити застосунок, працювати з базою й міграціями, зібрати й викотити
зміни. Синтаксис `.rhx` описано окремо — [SYNTAX.md](SYNTAX.md) (коротко для
LLM — [llms.txt](llms.txt), готові рецепти — [examples/cookbook](examples/cookbook)).

---

## 1. Встановити CLI

Найпростіше — завантажити готовий архів для своєї ОС зі сторінки
[релізів](https://github.com/lab4prog/rhaix/releases) і покласти `rhaix` у PATH.
Або зібрати з вихідного коду (потрібен Rust 1.88+):

```bash
cargo install rhaix-cli          # з crates.io
cargo install --path crates/rhaix-cli   # з клону репозиторію
```

Далі в посібнику команди пишуться як `rhaix …`. У клоні репозиторію те саме
працює й без встановлення: `cargo run -p rhaix-cli -- …`.

## 2. Створити застосунок

```bash
rhaix new myapp
cd myapp
rhaix dev .
```

`rhaix dev` підніме сервер розробки (за замовчуванням на `:3000`) із **живим
перезавантаженням**: правка `.rhx` видима в браузері за ~70 мс, без ручного
перезапуску.

Розкладка проєкту. `rhaix new` створює з неї мінімум — `rhaix.toml`,
`layouts/`, `pages/`, `components/`, `migrations/`, `public/`; решту тек
додають тоді, коли вони потрібні:

```
myapp/
  rhaix.toml            # конфіг: порт, база, [app], [mail]
  layouts/main.rhx      # єдина повна HTML-сторінка; решта потрапляє в <slot/>
  pages/                # сторінки: файл → маршрут (index.rhx → /, todo.rhx → /todo)
  partials/             # HTMX-фрагменти: Stats.rhx → /components/stats
  components/           # компоненти <TodoItem/> тощо (по HTTP недоступні)
  scripts/*.rhai        # спільні функції, видимі скрізь без import
  migrations/           # *.sql, застосовуються на старті
  public/               # статика: *.css і *.js самі підхоплюються в layout
  api/                  # JSON-ендпоінти: orders.rhx → /api/orders
  middleware.rhx        # виконується перед кожним запитом (охорона, локаль)
```

Правило маршрутів: структура тек і є маршрутами. `pages/blog/[id].rhx` →
`/blog/{id}`, значення читається як `req.param("id")`.

Якщо додатку потрібен ще й JSON для зовнішніх клієнтів — мобільного застосунку,
іншого сервісу, скрипта, — створіть теку `api/`. Файл `api/orders.rhx` стане
маршрутом `/api/orders` і віддаватиме JSON: layout не додається, повернена мапа
серіалізується сама, помилки теж приїжджають JSON-ом. Сесії там немає навмисно,
тому автентифікація — за токеном у заголовку (SYNTAX.md §6.7, рецепт у
[examples/cookbook/api](examples/cookbook/api)).

## 3. База даних і міграції

### Конфіг

`rhaix.toml`, секція `[db]`:

```toml
[db]
driver = "sqlite"
url    = "data/app.db"     # шлях відносно кореня проєкту, не теки запуску
```

Для PostgreSQL — той самий застосунок, інша секція:

```toml
[db]
driver = "postgres"
url    = "postgres://user:pass@localhost:5432/app"
```

Переносимий шар (`db.find/get/insert/update/delete/count`) і `?`-плейсхолдери в
`db.query(...)` однакові на обох. **Зміна драйвера — це зміна конфігу, а не
коду.** Переносимий шар очікує первинний ключ у колонці `id`.

### Міграції

Файл `migrations/NNN_назва.sql` — звичайний SQL. Нумерація задає порядок:

```sql
-- migrations/002_users.sql
create table users (
    id       integer primary key autoincrement,
    username text    not null unique,
    password text    not null,
    created  text    not null default (datetime('now'))
);
```

Міграції застосовуються **автоматично при старті** сервера (і `rhaix dev`, і
`rhaix serve`, і зібраний бінарник). Кожна застосовується один раз — облік
ведеться в таблиці `_rhaix_migrations`. Тому щоб додати колонку чи таблицю:

1. створіть новий файл `migrations/003_...sql` (не редагуйте вже застосований);
2. перезапустіть застосунок — нову міграцію буде застосовано, старі пропущено.

Кожна міграція йде однією транзакцією: або вся, або жодної.

> На PostgreSQL використовуйте типи Postgres: `serial primary key`,
> `numeric(12,2)`, `timestamptz`. `date()` розуміє `timestamptz`, `money()` —
> `numeric`.

## 4. Перевірити без запуску

```bash
rhaix check .          # компілює всі .rhx; невідомий компонент, цикл, помилка виразу
rhaix check . --json   # те саме для CI
```

`check` нічого не запускає й нічого не пише в проєкт. Ненульовий код виходу
зручний для CI.

## 5. Секрети, сесії, пошта в продакшні

- **Ключ підпису сесій.** У розробці `rhaix dev` створює файл `.rhaix-secret`
  (він у `.gitignore`). У продакшні задайте змінну оточення:

  ```bash
  export RHAIX_SECRET="довгий випадковий рядок"
  ```

  Без нього сесії не переживуть перезапуск, і про це буде попередження в лозі.

- **Пошта.** Без секції `[mail]` `mail.send(...)` друкує лист у лог (dev). Для
  справжнього SMTP додайте секцію — і `rhaix build` сам увімкне потрібне:

  ```toml
  [mail]
  from      = "App <noreply@example.com>"
  smtp_host = "smtp.example.com"
  smtp_port = 587
  smtp_user = "..."
  smtp_pass = "..."
  ```

- **CSRF** увімкнено за замовчуванням; форми й кнопки, що змінюють дані,
  фреймворк доповнює токеном сам. Вимкнути (наприклад, для публічного вебхука):
  `csrf = false` у `[app]`.

## 6. Деплой: один бінарник

```bash
rhaix build .
```

Ця команда вшиває **всі файли проєкту** в один виконуваний файл і збирає його
через `cargo build --release`. На виході — `myapp.exe` (або `myapp`) поруч із
проєктом. Він не читає з диска нічого, крім бази даних.

`rhaix build` сам обирає, що вкласти в бінарник, за `rhaix.toml`: драйвер із
`[db]` і пошту, якщо є `[mail]`. SQLite-застосунок без пошти не тягне ні
залежностей Postgres, ні TLS.

Деплой — **копіювання одного файлу**:

```bash
scp myapp user@server:/opt/myapp/
ssh user@server 'cd /opt/myapp && RHAIX_SECRET=... PORT=8080 ./myapp'
```

Бінарник слухає `0.0.0.0`, порт бере зі змінної `PORT` або з `rhaix.toml`.
Rust-тулчейн потрібен **для збірки, але не для запуску**.

Звідки `rhaix build` бере сам фреймворк: якщо `rhaix` встановлено з релізу чи
з crates.io — з crates.io, **рівно тієї версії**, що й сам CLI (тож збирати
треба з доступом до мережі або з прогрітим кешем cargo). Якщо `rhaix` зібрано з
клону репозиторію — із цього клону. Явно вказати теку: `--framework <тека>`.

> Альтернатива без збірки бінарника: `rhaix serve .` піднімає той самий
> застосунок **із диска** в режимі продакшн (заморожений кеш, стиснення). Це
> зручно, якщо код лежить на сервері й тулчейн там є.

## 7. Викотити зміни

Оновлення — це нова збірка й заміна файлу:

```bash
# на машині зі збіркою
rhaix build .
scp myapp user@server:/opt/myapp/myapp.new

# на сервері
mv myapp.new myapp        # атомарна заміна
# перезапустити процес (systemd/докер/вручну)
```

Що відбувається при перезапуску:

- **нові міграції застосовуються самі** (старі пропускаються за
  `_rhaix_migrations`);
- база (`data/app.db`) лишається на місці — вона поза бінарником;
- сесії переживуть перезапуск, **якщо** `RHAIX_SECRET` не змінювався.

Тому звичайний цикл оновлення: додати міграцію (за потреби) → `rhaix build` →
замінити файл → перезапустити. Відкату «на льоту» немає — тримайте попередній
бінарник поруч, щоб повернутися однією `mv`.

## 9. Редактор

Розширення для VS Code лежить у [editors/vscode](editors/vscode): підсвітка
`.rhx` плюс мовний сервер — діагностика прямо в редакторі, перехід до
компонента по `F12`, доповнення компонентів, директив і глобальних об'єктів.

`rhaix-lsp` є в архіві релізу поруч із `rhaix`, а саме розширення — файл
`rhaix-*.vsix` там само:

```bash
code --install-extension rhaix-1.2.1.vsix
```

Або з вихідного коду: `cargo install rhaix-lsp`.

Сервер нічого нового не перевіряє — він показує **ту саму** помилку, яку дає
`rhaix check`, поки її ще не видно в браузері. Без нього розширення працює
далі: лишається підсвітка.
