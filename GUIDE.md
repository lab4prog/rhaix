# rhaix — посібник

Як створити застосунок, працювати з базою й міграціями, зібрати, викотити й
оновити його. Мову `.rhx` і все, що доступне зі скрипта, описує
[SYNTAX.md](SYNTAX.md); стисло для LLM — [llms.txt](llms.txt); готові рецепти —
[examples/cookbook](examples/cookbook).

---

## 1. Встановити CLI

Найпростіше — завантажити архів для своєї ОС зі сторінки
[релізів](https://github.com/lab4prog/rhaix/releases) і покласти `rhaix` у PATH.
Або зібрати з вихідного коду (потрібен Rust 1.88+):

```bash
cargo install --git https://github.com/lab4prog/rhaix rhaix-cli
```

У клоні репозиторію те саме працює й без встановлення:
`cargo run -p rhaix-cli -- …`. Далі в посібнику команди пишуться як `rhaix …`.

| Команда | Що робить |
|---|---|
| `rhaix new <тека>` | створює проєкт |
| `rhaix dev [тека] [--port N]` | сервер розробки з живим перезавантаженням |
| `rhaix check [тека] [--json]` | перевіряє проєкт без запуску (4) |
| `rhaix serve [тека] [--port N]` | той самий застосунок у режимі продакшну, з диска (6) |
| `rhaix build [тека]` | один бінарник з усіма файлами всередині (6) |
| `rhaix openapi [тека] [-o файл]` | опис `api/` у форматі OpenAPI 3.1 (SYNTAX.md §6.7) |
| `rhaix eject ui [--force]` | забирає тости й модалки в `public/rhaix-ui.js` (SYNTAX.md §7.7) |

## 2. Створити застосунок

```bash
rhaix new myapp
cd myapp
rhaix dev .
```

`rhaix dev` піднімає сервер розробки на `http://localhost:3000` із **живим
перезавантаженням**: правка `.rhx` видима в браузері за ~70 мс. Помилки
показуються прямо на сторінці, з файлом, рядком і підказкою.

`rhaix new` створює мінімум — `rhaix.toml`, `layouts/`, `pages/`,
`components/`, `migrations/`, `public/`. Решту тек додають, коли вони потрібні:

```
myapp/
  rhaix.toml            # конфіг: порт, база, [app], [mail], [api]
  layouts/main.rhx      # єдина повна HTML-сторінка; решта потрапляє в <slot/>
  pages/                # сторінки: файл → маршрут (index.rhx → /, todo.rhx → /todo)
  partials/             # HTMX-фрагменти: Stats.rhx → /components/stats
  components/           # компоненти <TodoItem/> тощо (по HTTP недоступні)
  api/                  # JSON-ендпоінти: orders.rhx → /api/orders
  middleware.rhx        # виконується перед кожним запитом (охорона, локаль)
  scripts/*.rhai        # спільні функції, видимі скрізь без import
  migrations/           # *.sql, застосовуються на старті
  locales/*.toml        # переклади для t("ключ")
  public/               # статика: *.css і *.js самі підхоплюються в layout
  native/lib.rs         # власні функції на Rust (8)
```

Структура тек і є маршрутами: `pages/blog/[id].rhx` → `/blog/{id}`, значення
читається як `req.param("id")`.

Якщо застосунку потрібен JSON для зовнішніх клієнтів — мобільного застосунку,
іншого сервісу, скрипта, — створіть теку `api/`. Файл `api/orders.rhx` стане
маршрутом `/api/orders`: layout не додається, повернена мапа серіалізується
сама, помилки теж приїжджають JSON-ом. Сесії там немає навмисно, тому
автентифікація — за токеном у заголовку (SYNTAX.md §6.7, рецепт у
[examples/cookbook/api](examples/cookbook/api)).

## 3. База даних і міграції

### Конфіг

`rhaix.toml`, секція `[db]`:

```toml
[db]
driver = "sqlite"
url    = "data/app.db"     # шлях відносно кореня проєкту, не теки запуску
```

Для PostgreSQL — той самий застосунок, інша секція:

```toml
[db]
driver = "postgres"
url    = "postgres://user:pass@localhost:5432/app"
pool   = 16                 # скільки з'єднань тримати; решта запитів чекає
```

Переносимий шар (`db.find/get/insert/update/delete/count`) і `?`-плейсхолдери в
`db.query(...)` однакові на обох драйверах. **Зміна драйвера — це зміна конфігу,
а не коду.** Переносимий шар очікує первинний ключ у колонці `id`. Усе про `db`
— SYNTAX.md §7.10.

### Пул з'єднань

Застосунок тримає не більше `pool` з'єднань (типово 16 для Postgres і 8 для
SQLite) і повторно використовує підготовлені запити на кожному з них. Коли всі
з'єднання зайняті, запит чекає вільного до 30 с, а не відкриває нове.

Postgres за замовчуванням дозволяє 100 з'єднань на весь сервер. Кілька копій
застосунку за балансиром ділять цей ліміт між собою: чотири копії з
`pool = 16` — це вже 64.

### Міграції

Файл `migrations/NNN_назва.sql` — звичайний SQL. Нумерація задає порядок:

```sql
-- migrations/002_users.sql
create table users (
    id       integer primary key autoincrement,
    username text    not null unique,
    password text    not null,
    created  text    not null default (datetime('now'))
);
```

Міграції застосовуються **автоматично при старті** — і `rhaix dev`, і
`rhaix serve`, і зібраного бінарника. Кожна застосовується один раз: облік
ведеться в таблиці `_rhaix_migrations`, а сама міграція йде однією транзакцією —
або вся, або жодної. Щоб додати колонку чи таблицю:

1. створіть новий файл `migrations/003_...sql` (не редагуйте вже застосований);
2. перезапустіть застосунок — нову міграцію буде застосовано, старі пропущено.

> На PostgreSQL використовуйте типи Postgres: `serial primary key`,
> `numeric(12,2)`, `timestamptz`. `date()` розуміє `timestamptz`, `money()` —
> `numeric`.

## 4. Перевірити без запуску

```bash
rhaix check .          # компілює всі .rhx: невідомий компонент, цикл, помилка виразу
rhaix check . --json   # те саме для CI й редакторів
```

`check` нічого не запускає й нічого не пише в проєкт. Помилки дають ненульовий
код виходу, тож команда зручна в CI.

Крім помилок, `check` попереджає про те, що компілюється, але робить не те
(код виходу від цього не змінюється):

| Попередження | Що не так |
|---|---|
| `<td>{c.name}</td>` | одинарні дужки в тексті — просто символи; треба `{{ c.name }}` |
| `@class={#{"selected": …}}` | `selected`, `checked`, `disabled` — атрибути, а не класи; треба `@attr` |
| layout без `<rhaix:head/>` | скрипти фреймворку виконуються знову на кожному boosted-переході |
| невідомий ключ у `rhaix.toml` | `minify_html = true` чи `sesion_days = 7` ніхто не читає; є підказка |
| `for c in rows { c.total = … }` | змінна циклу — копія, масив не зміниться; треба `rows[i].total = …` |

## 5. Секрети, сесії, пошта в продакшні

- **Ключ підпису сесій.** У розробці `rhaix dev` створює файл `.rhaix-secret`
  (він у `.gitignore`). У продакшні задайте змінну оточення:

  ```bash
  export RHAIX_SECRET="довгий випадковий рядок"
  ```

  Без неї сесії не переживуть перезапуск, і про це буде попередження в лозі.

- **Пошта.** Без секції `[mail]` `mail.send(...)` друкує лист у лог. Для
  справжнього SMTP додайте секцію — і `rhaix build` сам увімкне потрібне:

  ```toml
  [mail]
  from      = "App <noreply@example.com>"
  smtp_host = "smtp.example.com"
  smtp_port = 587
  smtp_user = "..."
  smtp_pass = "..."
  ```

- **CSRF** увімкнено за замовчуванням; форми й кнопки, що змінюють дані,
  фреймворк доповнює токеном сам. Вимкнути для всього застосунку (наприклад,
  заради публічного вебхука): `csrf = false` у `[app]`.

Усі ключі `rhaix.toml` з типовими значеннями — SYNTAX.md §13.

## 6. Деплой

### Один бінарник — `rhaix build`

```bash
rhaix build .
```

Команда вшиває **всі файли проєкту** в один виконуваний файл і збирає його
через `cargo build --release`. На виході — `myapp.exe` (або `myapp`) поруч із
проєктом. Він не читає з диска нічого, крім бази даних.

`rhaix build` сам обирає, що вкласти в бінарник, за `rhaix.toml`: драйвер із
`[db]` і пошту, якщо є `[mail]`. SQLite-застосунок без пошти не тягне ні
залежностей Postgres, ні TLS. Rust-тулчейн потрібен **для збірки, але не для
запуску**.

Деплой — **копіювання одного файлу**:

```bash
scp myapp user@server:/opt/myapp/
ssh user@server 'cd /opt/myapp && RHAIX_SECRET=... PORT=8080 ./myapp'
```

Бінарник слухає `0.0.0.0`, порт бере зі змінної `PORT` або з `rhaix.toml`.

**Звідки `rhaix build` бере сам фреймворк.** Якщо `rhaix` зібрано з вихідного
коду (клон або `cargo install --git`), — із цього вихідного коду, тієї самої
версії. Бінарник із релізу шукає фреймворк на crates.io, але там rhaix ще не
опубліковано. Тому з релізним `rhaix` вкажіть клон репозиторію явно:

```bash
git clone https://github.com/lab4prog/rhaix --branch v1.6.3
rhaix build . --framework ./rhaix
```

### Без збірки — `rhaix serve`

`rhaix serve .` піднімає той самий застосунок **із диска** в режимі продакшну:
заморожений кеш шаблонів, стиснення, кешування статики. Зручно, якщо код лежить
на сервері. Проєкт із `native/` при цьому потребує Rust-тулчейну (8).

`rhaix serve` і `rhaix dev` слухають лише `127.0.0.1` і `::1`: назовні їх
публікують через зворотний проксі.

### За nginx чи Caddy

За проксі `req.ip` — це завжди адреса проксі, і ліміти спроб рахувались би на
всіх разом. Увімкніть:

```toml
[server]
trust_proxy = true   # req.ip — з останнього запису X-Forwarded-For
```

Вмикайте це **лише** тоді, коли застосунок недосяжний інакше як через ваш
проксі: `X-Forwarded-For` може підставити будь-хто. Живі оновлення (SSE,
`/_rhaix/live`) працюють за nginx без налаштувань: відповідь іде із заголовком
`X-Accel-Buffering: no`.

## 7. Викотити зміни

Оновлення — це нова збірка й заміна файлу:

```bash
# на машині зі збіркою
rhaix build .
scp myapp user@server:/opt/myapp/myapp.new

# на сервері
mv myapp.new myapp        # атомарна заміна
# перезапустити процес (systemd, docker, вручну)
```

Що відбувається при перезапуску:

- **нові міграції застосовуються самі**, старі пропускаються за
  `_rhaix_migrations`;
- база (`data/app.db`) лишається на місці — вона поза бінарником;
- сесії переживуть перезапуск, **якщо** `RHAIX_SECRET` не змінювався.

Звичайний цикл оновлення: додати міграцію (за потреби) → `rhaix build` →
замінити файл → перезапустити. Відкату «на льоту» немає: тримайте попередній
бінарник поруч, щоб повернутися однією `mv`. Міграцію, яку вже застосовано,
старий бінарник не відкотить — робіть їх сумісними з попередньою версією коду
(додати колонку можна, перейменувати — у два кроки).

## 8. Власний код на Rust

Коли Rhai не вистачає — важкі обчислення, чужий Rust-крейт, — додайте
`native/lib.rs` із функцією `pub fn register(engine: &mut Engine)`. Залежності
пишуться в `native/dependencies.toml`. `rhaix build` вшиває цей код у бінарник,
а `rhaix dev` і `rhaix serve` збирають із ним власний сервер через cargo
(у `target/rhaix-native/`). Rust-тулчейн тут потрібен і для розробки. Приклад і
деталі — SYNTAX.md §7.9.

## 9. Редактор

Розширення для VS Code лежить в [editors/vscode](editors/vscode): підсвітка
`.rhx` плюс мовний сервер — діагностика прямо в редакторі, перехід до
компонента по `F12`, доповнення компонентів, директив і глобальних об'єктів.

`rhaix-lsp` є в архіві релізу поруч із `rhaix`, а саме розширення — файл
`rhaix-<версія>.vsix` там само:

```bash
code --install-extension rhaix-<версія>.vsix
```

Або з вихідного коду: `cargo install --git https://github.com/lab4prog/rhaix rhaix-lsp`.

Сервер нічого нового не перевіряє — він показує **ту саму** помилку, яку дає
`rhaix check`, поки її ще не видно в браузері. Без нього розширення працює
далі: лишається підсвітка.
