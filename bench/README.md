# rhaix проти Astro — чесне порівняння

Друга половина воріт M9 з `RISKS.md`: «один реальний застосунок; писати швидше,
ніж на Astro для цього класу задач».

Тут два застосунки, які роблять **те саме**: список замовлень із фільтром і
сортуванням, сторінка замовлення, форма з валідацією, HTMX-фрагмент. Обидва
читають **один і той самий файл SQLite** з 1000 записів.

---

## 1. Що саме порівнюється

| | rhaix | Astro |
|---|---|---|
| Застосунок | `bench/rhaix-orders` | `bench/astro-orders` |
| Режим | `rhaix serve` (продакшн) | `output: "server"`, адаптер `@astrojs/node`, `astro build` |
| База | `bench/data/orders.db`, драйвер rhaix | той самий файл, `node:sqlite` |
| Порт | 4322 | 4321 |

Вивід сторінок збігається символ у символ (з точністю до пробілів) — це
перевірялось перед вимірами.

### Відтворити

```bash
# база на 1000 записів
python bench/seed.py

# rhaix
cargo build --release -p rhaix-cli
./target/release/rhaix serve bench/rhaix-orders --port 4322

# astro
cd bench/astro-orders && npm install && npm run build
ORDERS_DB=../data/orders.db PORT=4321 node --experimental-sqlite ./dist/server/entry.mjs

# заміри
npx autocannon -c 1 -d 10 http://127.0.0.1:4322/orders/5
```

Залізо: AMD Ryzen 5 5600H, 12 потоків, Windows 11. Навантаження — `autocannon`
(інструмент зі світу Node, щоб не було питань до власного генератора).
**Стиснення вимкнене з обох боків** — перевірено: 1050 байтів на відповідь при
тілі 892 байти, тобто тіло не стискалося.

## 2. Один запит за раз (`-c 1`)

Головна колонка. Вона не залежить від кількості ядер, тому порівнює саме
**вартість рендеру одного запиту**.

| Сценарій | rhaix | Astro | |
|---|---|---|---|
| сторінка замовлення (1 рядок) | **893 req/s** (1.1 мс) | 716 req/s (1.4 мс) | rhaix ×1.25 |
| таблиця, 330 рядків | **146 req/s** (6.8 мс) | 89 req/s (11.2 мс) | rhaix ×1.6 |
| фрагмент, 1000 рядків | **61 req/s** (16.4 мс) | 39 req/s (25.6 мс) | rhaix ×1.6 |

## 3. П'ятдесят одночасних запитів (`-c 50`)

Як воно розгортається за замовчуванням: адаптер Node — один процес на одному
ядрі, rhaix — tokio на всіх дванадцяти.

| Сценарій | rhaix req/s | p99 | Astro req/s | p99 |
|---|---|---|---|---|
| сторінка замовлення | **3639** | 16 мс | 860 | 74 мс |
| таблиця, 330 рядків | **490** | 228 мс | 106 | 525 мс |
| фрагмент, 1000 рядків | **202** | 436 мс | 42 | 1237 мс |

**Цю таблицю не можна читати як «Rust у 4 рази швидший за JS».** Різниця тут
здебільшого в тому, що один процес Node використовує одне ядро з дванадцяти.
Штатна відповідь у світі Node — запустити 12 процесів за балансиром; це дасть
приблизно ×12 до пропускної здатності й приблизно ×12 до пам'яті. Чесна
колонка — розділ 2.

## 4. Куди йде час

Три сторінки, які відрізняються рівно одним шаром (`-c 1`, мс на запит):

| Що робить сторінка | rhaix | Astro |
|---|---|---|
| лише запит до бази, 1000 рядків | 2.8 | 5.6 |
| + рендер 5000 простих комірок | 5.9 **(+3.1)** | 13.8 **(+8.2)** |
| + 4000 викликів хелперів (`money`, `date`, `status_label`) | 17.3 **(+11.4)** | 25.8 **(+12.0)** |

- Шар даних rhaix швидший удвічі.
- Простий рендер швидший у 2.6 раза: `{{ o.title }}` не доходить до рушія Rhai
  взагалі — це швидкий шлях, доданий у M1.
- **Виклики функцій — паритет.** Тут переваги в rhaix немає: 4000 викликів
  коштують 11.4 мс проти 12.0 мс у V8. Саме вони, а не фреймворк, визначають
  час важкої сторінки.

## 5. Що це порівняння знайшло в rhaix

До виправлення ця ж таблиця виглядала інакше:

| | rhaix | Astro |
|---|---|---|
| повна таблиця 1000 рядків, було | 32.5 мс | **24.8 мс** |
| стало | **17.3 мс** | 25.8 мс |

Astro був швидшим — і причина знайшлася в одній функції. `date()` будував
масив із дванадцяти готових рядків **на кожній позиції шаблону**: для шаблону
`"DD.MM.YYYY HH:mm"` це близько 190 алокацій на виклик, тобто 190 тисяч на
таблицю в 1000 рядків. Після переписування на пряме дописування в буфер
сторінка стала вдвічі швидшою.

Без порівняння з чужим фреймворком цього не було б видно: власні бенчмарки M0 і
M1 міряли прості вирази й показували цілком пристойні 7.34 мс на 1000 рядків.

## 6. Решта цифр

| | rhaix | Astro |
|---|---|---|
| Пам'ять після навантаження (RSS) | **22 МБ** | 154 МБ |
| Холодний старт до першої відповіді | **173 мс** | 721 мс |
| Що треба покласти на сервер | один файл, **12.0 МБ** | `dist/` 434 КБ + Node + `node_modules` (152 МБ у розробці) |
| Рядків коду на ту саму функціональність | **185** | 287 |

Різниця в рядках — не про лаконічність синтаксису. Вона майже повністю в двох
файлах, яких у rhaix просто немає:

- `src/lib/db.js` (32 рядки) — шар доступу до бази, у rhaix це `db.find`;
- `src/lib/format.js` (36 рядків) — `money()`, `date()`, `url()`, у rhaix це
  стандартна бібліотека.

Плюс правило фрагмента: Astro про HTMX не знає, тому `index.astro` довелося
розділити на сторінку й компонент `OrdersTable.astro`, щоб не дублювати вміст у
двох гілках `isHtmx ? … : …`. У rhaix те саме робиться без жодного рядка.

## 7. Чого це порівняння **не** показує

Читати попередні розділи без цього — нечесно.

1. **Островів у rhaix немає й не буде.** Astro вміє віддавати React/Vue/Svelte
   компоненти з гідратацією; це велика частина його цінності й тут не
   виміряна взагалі. Якщо задача вимагає клієнтського стану, Astro виграє
   не на відсотки, а за визначенням.
2. **Екосистема.** npm проти «те, що зареєстроване в рушії». Для rhaix це
   найбільший ризик, і жоден бенчмарк його не закриває.
3. **Одне ядро проти дванадцяти** в розділі 3 — див. застереження там-таки.
4. **`node:sqlite` — експериментальний** модуль Node 22. `better-sqlite3` міг би
   дати інші цифри на шарі даних.
5. **CSRF у бенчмарку rhaix вимкнено** (`csrf = false`), щоб генератор
   навантаження міг слати POST без попереднього GET. На GET-сценаріях, а це всі
   виміряні, він і так не працює.
6. **Один застосунок — не статистика.** Це задача класу «внутрішній інструмент
   зі списками й формами». Для інших класів висновки не переносяться.

## 8. Висновок

Для того класу задач, на який фреймворк і розрахований, rhaix **швидший у
півтора раза на запит**, тримає в сім разів менше пам'яті, стартує вчетверо
швидше й розгортається одним файлом. Код на 35% коротший — переважно тому, що
шар даних, форматування й правило фрагмента вже всередині.

Але найкорисніший результат цього порівняння — не таблиця, а знайдений баг.
Рівно один хибний рядок у `date()` коштував удвічі більшого часу відповіді й
перевертав підсумок на користь Astro.
